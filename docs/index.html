Which pages should a content reviewer check first?

Some pages that rank well in search still get far fewer clicks than similar pages at the same rank. Using a March 2026 slice of FlyRank's production search data (12,023 visible pages, drawn from a 9.8-million-row monthly warehouse), I built a simple rule baseline, then a Logistic Regression model, to flag which pages are worth a content reviewer's time first. Under an honest client-grouped test split, the model reaches 40.0% precision@50 — a real lift over both random guessing (26.1%) and a naive position-only rule (34.0%), though far short of a circular baseline I deliberately caught and discarded. This is decision-support for prioritizing manual review, not a proven fix, and not tested outside the page-visibility range it was trained on.

01The problem

A content reviewer opens their dashboard and sees thousands of pages. Some are getting fewer clicks than they should — but a low click count on its own means nothing. A page ranked 15th getting 0.2% clicks might be completely normal. The same 0.2% on a page ranked 3rd is a real problem. Telling those two situations apart, by eye, across thousands of pages, isn't realistic for one person to do manually.

This work answers one question: which pages, ranked where they are, are getting fewer clicks than similar pages nearby — and are worth a reviewer's time to check first?

The stakes here are genuinely low on both sides, which matters for how this should be used. If a flagged page turns out fine, a reviewer loses a few minutes. If a real problem page gets missed, it's a missed opportunity, not a crisis. That asymmetry is part of why a scoring approach — imperfect, honest about its limits — is a reasonable tool here, rather than something that needs to be perfect before it's useful.

02Data

Source and scope. I used FlyRank's Hugging Face-hosted warehouse, scoped to March 2026 — a safe middle month, deliberately not the most recent month, which is reserved as a sealed test set.

Grain, verified. One row = one page's performance on one day. March 2026 has 9,841,378 rows across 331,437 distinct pages. I confirmed the grain with a group-by check (page + client + date) that returned zero duplicate groups.

Only 36.7% of rows (3,611,061) have usable search data (gsc_data_available = TRUE). Pages or clients with short search history are effectively invisible in this slice — findings here may not generalize evenly across all of FlyRank's clients.

The working slice used throughout my baseline, model, and validation: pages with impressions_90d ≥ 500 and avg_position between 1-20 — "actually visible in search" — narrowing to 12,023 pages.

Deliberately excluded, and why:

  • AI-assistant referral columns (ai_chatgpt, ai_perplexity, etc.) — not relevant to this question
  • trend_direction, trend_pct — flagged as label-source fields, never safe as features
  • ctr, all click-count columns — these define my own label, so using them as features would be circular
  • Post-click behavior columns (pageviews_90d, engagement_rate, etc.) — downstream of the outcome, not a legitimate input
  • FlyRank's own product flags (health_score, needs_ctr_fix, etc.) — confirmed absent from this dataset entirely

Public-safe: all IDs are pseudonymous hashes, used only for grouping the train/test split — never as features, never shown alongside anything identifying.

03Methodology

Baseline (a rule, before any model). Score = how far a page's CTR falls below the median CTR of other pages in its own position tier (tier_median_ctr − page_ctr, floored at 0). Reason code: ctr_below_tier_peers. Action: review title and meta description.

Two signal checks shaped this rule. Signal A tested whether CTR actually drops as position worsens — verdict MIXED (the worst tier was clearly worse, but the very best tier didn't beat the next one down, likely a small-sample effect). Signal B tested whether high-traffic pages have more room to improve — verdict OPPOSITE (high-traffic pages were already outperforming their tier, not underperforming). Because of Signal B, traffic volume is used only as an eligibility gate, never as a score multiplier.

Model. Logistic Regression — the question is "which pages to check first" (a ranking question), not a fixed label, so a classifier's predicted probability gives a natural ranking, and its coefficients stay readable enough to explain in plain words.

Label. No reviewer has manually confirmed which pages truly have a title problem, so I used a proxy: the top 25% of CTR gaps. This is grounded in a real, observed number, not someone else's rule.

Features. 20 columns describing a page before anyone clicks (search demand, competition, content type, position, freshness, and similar). Deliberately excluded: CTR, all click-count columns, post-click behavior, and any FlyRank product flag — using any of these would let a model read back its own label instead of learning a real pattern.

Split. Grouped by client, not random — confirmed zero client overlap between train and test. This matters: a random split lets the same client's pages leak between train and test, which (see Results) inflates the score artificially.

Leakage checks, run twice. First, a deliberate "cheat" feature built from the answer itself: an honest model scored 0.0158, and adding the cheat column jumped it to a suspicious 1.0000 — confirming the leak trap works. Second, a full audit of the final feature set against three leakage categories (label-derived, future-window, product-flag) — all three came back empty.

04Results

My first comparison table showed the rule-based baseline scoring a perfect 1.000 precision@50 — too good to be true, and it was. The label is defined directly from the same number the baseline ranks by, so it wasn't predicting anything; it was reading back its own answer key. That's not a real test.

A circular evaluation doesn't just look wrong in hindsight — it actively hides whether a model is doing real work. Catching this before reporting it is what separates a checked result from an assumed one.

For a fair comparison, every method below is measured the same way, on the same held-out test rows, against a naive rule that doesn't share any information with the label:

Base rate (random guessing)26.1%

The rule-based baseline (1.000) is omitted here as invalid — see above.

The gap between the random-split score (72.0%) and the honest grouped-split score (40.0%) is itself a finding: 32 points of that "performance" was the model partly memorizing specific clients, not learning anything general. The number I trust and report is 40.0% — a real, modest lift over both random guessing and the naive rule, on clients the model never saw during training.

05Limitations

  • Proxy label, not human-confirmed. "Needs review" means "top 25% CTR gap," not "a person checked and confirmed the title is broken." A large gap can come from cannibalization, seasonality, or a search feature capturing the click — not only a bad title.
  • Cross-sectional, not causal. This is one snapshot, no before/after test. The right claim is "this page looks worth reviewing," never "fixing the title will improve CTR."
  • Narrow, verified boundaries. Trained and tested on 28 clients, impressions 500–517,715, positions 0.2–20.0. No evidence this ranking holds outside that range.
  • A real error pattern. The model over-trusts recent updates as a signal of "this page is fine" — three of its most confident wrong predictions were all pages updated in the last 30 days that still had large, real CTR gaps.

One example of walking a claim back to what the evidence actually supports: an early draft called one flagged page "my strongest pick." That page does have real search demand, real visibility, and zero clicks — but "strongest pick" implied a fix would work, which was never tested. The honest version: "this page looks worth reviewing first, because the combination of visibility and zero clicks is unusual — whether a title change would help hasn't been tested."

06Ranked recommendations

The final output is a ranked queue, not a bare score — each page carries a plain-language reason built from its own features, so a reviewer can trust it in seconds rather than interpreting a number.

Example reason: "ranks on page 1; hasn't been updated in 210 days; has real search demand (320/mo)." Every row gets the same action (review title and meta description) and the same reason code (model_flagged_likely_underperformer), ranked by predicted probability.

What a reviewer must check before acting: the actual title and content, not just the score; whether a sibling page on the same site might be capturing the click instead; whether the tracked keyword has any real measured search volume at all.

What should never be automated: publishing a new title without human review; deprioritizing a page based on a low score (a low score means "not flagged," not "confirmed fine"); using this score in any client-facing report or billing decision.

Signs this playbook has gone stale: a large shift in the overall base rate (currently 26.1%); new clients very different from the 28 in this training set; content types or providers that never appeared in training; reviewers reporting flagged pages "look fine" more often than the measured 40.0% precision would predict.
